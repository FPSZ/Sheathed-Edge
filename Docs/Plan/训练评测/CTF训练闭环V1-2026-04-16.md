# CTF 训练闭环 V1（Agent Router + Skills + Tool Trajectory）

## Summary

这份方案把当前本地系统的 CTF 训练主线正式固定为：

- `agent.md` 做总路由
- 按 `task_family` 动态命中对应 `skill.md`
- 优先训练“题型判断 + 工具使用 + 证据收束”
- 先用**有本地 WP 可核对的公开题**做开发集
- 等公开题稳定后，再进入 `D:/CTF` 中带 WP 的本地赛题

当前阶段不追求“立刻把所有题都训会”，而是先把下面四件事训稳：

1. 会不会先走对题型路线
2. 会不会真实调用工具
3. 会不会根据工具结果继续推进
4. 会不会在拿到足够证据后停止枚举并收束回答

## 当前最适合应用的外部方法：结论

如果只问一个“最适合你当前阶段”的外部参考，结论分两半：

### 训练方法上最适合借鉴：`CTF-Dojo`
最值得借鉴的是它强调的：
- 少量但高质量、可验证的轨迹
- 执行验证优先于海量脏数据
- 先把 agent 的真实行为链稳定下来

这和你现在的系统非常契合，因为你已经有：
- Gateway
- tool-router
- MCP 工具链
- agent/skills
- 本地题目和 WP

你缺的不是“更多题”，而是“高质量可验证 solve trajectory”。

### 评测与开发流程上最适合借鉴：`NYU CTF Bench`
最值得借鉴的是它把：
- `development set`
- `held-out eval set`
- benchmark agent pipeline

分得很清楚。

这对你当前最重要，因为你现在还在频繁改：
- `agent.md`
- `binary-core.md`
- `reverse/pwn/web skills`
- Gateway native tool prompt
- stopping rule

如果没有明确的开发集 / 保留评测集，你很快就会把 prompt 调到只会“记住这些题”。

### 最终判断
- **如果问训练方法：`CTF-Dojo` 最适合你当前阶段**
- **如果问评测组织：`NYU CTF Bench` 最适合你当前阶段**
- **如果问是否能直接照搬项目：都不能直接照搬，只能吸收方法**

你当前最合理的做法不是“照搬某个项目”，而是：
- 用 `NYU CTF Bench` 的开发/评测分层思想
- 用 `CTF-Dojo` 的高质量轨迹优先思想
- 落到你自己的 `agent router + skills + local tools + local cases` 体系里

## 为什么不是直接上大规模微调

当前不适合一上来就重 SFT / DPO / RL，原因很明确：

1. 你的 prompt scaffold 还在快速迭代期
2. 工具使用行为刚刚打通，还没稳定
3. 小模型最怕把错误 route / 错误 skill / 错误工具循环学进去
4. 现在最值钱的是先把失败模式分类清楚

所以 V1 固定采用：

- `skills-first`
- `tool-trajectory-first`
- `eval-first`
- `human-reviewed dataset second`
- `SFT after enough reviewed cases`

## 训练闭环 V1：固定流程

### Phase 0：固定题型路由和技能装配
先固定运行结构：

- `agent.md` 只负责：
  - `task_family`
  - `shared_domain`
  - `phase`
  - `primary_skill`
  - `next evidence target`
- `binary-core.md` 只负责 binary 共用底座
- `reverse/pwn/web skills` 只负责 family-specific checklist

固定规则：
- 不把所有知识堆回一个长 system prompt
- 不全文注入所有 skills
- 先路由，再注入对应 family skill

### Phase 1：开发集工具闭环
当前先拿 **有本地 WP 的 reverse 公开题** 做开发集。

V1 当前已经落地的 manifest：
- `D:/AI/Local/Datasets/reverse/manifests/reverse-writeup-backed-devset.v1.json`

当前先用 5 题起步：
- `nssctf-simplebase`
- `buuctf-level1`
- `buuctf-reverse1`
- `buuctf-transform`
- `nssctf-checkin`

目标不是直接训练，而是先反复跑通：
- 路由
- tools
- 证据摘要
- 收束

### Phase 2：review queue 结构化入库
每跑完一题，都先进入：
- `D:/AI/Local/Datasets/reverse/review_queue/<case_id>/case.json`

这些 case 先**不直接入 train**，而是：
- 等人工 review
- 补 teacher trace
- 打 error tags
- 决定是否可训练 / 可评测

### Phase 3：从 case 里抽技能增量
每道失败题或半成功题，都要抽出：
- 题型判断错了没有
- 工具顺序错了没有
- 是否重复枚举
- 是否没有在足够证据后收束
- 是否把 reverse 说成 pwn

这些不先喂模型，而是先变成：
- `agent.md` 修订
- `binary-core.md` 修订
- `reverse-skills.md` 修订
- Gateway tool stopping rule 修订

### Phase 4：达到门槛后再开始 SFT
只有当以下条件成立，才开始正式 SFT：

- 开发集 solve rate 稳定上升
- 工具调用不再只是口头建议
- 重复枚举明显下降
- 已积累足够多 `teacher-reviewed` case
- `train/dev/eval` 已分开

## 2026-04-16 AWDP 红蓝分层更新

本轮已把原有的 `agent router + binary-core + reverse/pwn/web` 结构，进一步升级为：

- `agent router`
- `binary-core`
- `awdp-core`
- `reverse skills`
- `pwn skills`
- `web skills`
- `awdp-red skills`
- `awdp-blue skills`

### 这次为什么要加这一层

原因很直接：
- `AWDP` 不是题型，而是比赛模式
- `red / blue` 不是 family，而是角色工作流
- `reverse / pwn / web` 仍然要保留成技术 family
- 不能把“修补题”“红队题”硬塞成新的 `task_family`

所以现在的稳定概念改成：

- `task_family = reverse | pwn | web | uncertain`
