# 参考架构可吸收部分优先级清单

日期：2026-04-01

## 写在前面

这份文档不是上一份《参考架构优缺点对比报告》的重复版，也不是“要不要迁移参考架构”的讨论稿。它只做一件事：把参考架构里真正值得吸收的内部 runtime 设计拆出来，按两个维度排序清楚：

- 当前阶段优先级：现在最该先补什么
- 长期架构价值优先级：未来最值钱的 runtime primitive 是什么

文档的评价标准固定围绕你们当前系统的真实目标：

- 比赛稳定性
- 训练前封板
- 过程监督与数据质量
- 后续 `skills-first + eval-first + human-in-the-loop + SFT second`

本文明确不讨论以下方向：

- 不讨论整体部署形态照搬
- 不讨论把 `Gateway + Tool Router + Admin + Host Agent` 收回单体
- 不讨论 UI 风格和产品表层交互
- 不把 `Tool Router / Admin / Host Agent` 写成待合并对象

## 这份清单解决什么问题

上一份总报告已经回答了“参考架构强在哪、你们当前系统强在哪、哪些不要照搬”。  
这份清单进一步回答一个更落地的问题：

1. 参考架构里哪些部件真的值得学
2. 这些部件当前先学什么、后学什么
3. 这些部件长期最值钱的是什么
4. 每一项更适合吸收到 `Gateway`、`Tool Router` 还是 `Admin`

本文主结论先行：

- 你们当前系统的优势仍然是清晰的 `Execution Plane + Control Plane`
- 当前最该补的不是外围控制面，而是 `Gateway` 内部偏薄的 `Conversation Runtime`
- 参考架构最值得吸收的是内部执行核心、恢复、上下文装配、工具结果沉淀与事件建模
- 吸收方式应以“低风险内收”为主，不做大重构

## 排序口径与判断标准

### 当前阶段优先级

排序依据看 4 件事：

- 是否直接提升比赛稳定性
- 是否直接提升训练前数据质量
- 是否能在不破坏多服务边界下低风险吸收
- 是否能为后续 `skills + eval + process supervision` 打基础

### 长期架构价值

排序依据也看 4 件事：

- 是否能成为稳定的 runtime primitive
- 是否能统一会话内行为建模
- 是否能提升恢复、评测、训练的一致性
- 是否值得作为未来系统中枢能力

## 当前阶段优先级总览

| 优先级 | 可吸收项 | 建议落点 | 当前判断 |
| --- | --- | --- | --- |
| P0 | Conversation Runtime | Gateway | 当前最缺的内核抽象，应优先补强 |
| P0 | Runtime Event Model | Gateway | 直接决定过程监督、轨迹抽样、评测可复跑 |
| P0 | Tool Result Persistence / Context Compaction | Gateway | 对长对话、工具大输出、训练前结构化最直接 |
| P0 | Plan / Recovery Layer | Gateway | 对恢复、回放、过程复盘和训练前抽样很关键 |
| P1 | Context Assembly | Gateway | 提升一致性，但即时收益略低于 P0 |
| P1 | Session Continuity | Gateway | 很重要，但依赖前面 runtime 收口 |
| P1 | Tool Schema / Metadata Cache | Gateway | 有助于稳定工具上下文和 token 开销 |
| P1 | Command Queue / Scheduling | Gateway | 值得单列，但当前不是第一阻塞项 |
| P2 | MCP Support Internals | Gateway / Admin | 有价值，但当前不如 runtime 本体紧迫 |
| P2 | 更深的一体化 runtime 抽象 | Gateway | 长期可以做，当前不宜扩大战线 |
| P2 | 更复杂的 lifecycle / activity manager | Gateway | 当前收益不如 P0/P1，且改造面更大 |
| P2 | 多 agent / teammate 协作层 | Gateway / Admin | 现在不是主战场 |

当前阶段的主线建议只有一句：

> 先补 `Gateway` 内部的 `Conversation Runtime + Runtime Events + Tool Result Persistence + Plan/Recovery`，暂不动 `Tool Router / Admin / Host Agent` 边界。

## 长期架构价值总览

| 长期等级 | 可吸收项 | 长期判断 |
| --- | --- | --- |
| L1 | Conversation Runtime | 未来整个系统最像“中枢内核”的能力 |
| L1 | Plan / Recovery Layer | 决定恢复、回放、评测和训练前结构化的一致性 |
| L1 | Runtime Event Model | 决定日志、评测、训练监督是否能统一语言 |
| L2 | Context Assembly | 是稳定 runtime 的关键支撑层 |
| L2 | Tool Result Persistence / Context Compaction | 决定长上下文质量和工具输出治理能力 |
| L2 | Session Continuity | 决定跨重启、跨 turn 的连续性质量 |
| L2 | Tool Schema / Metadata Cache | 决定工具上下文稳定性与成本控制 |
| L3 | Command Queue / Scheduling | 有价值，但不应抢占前面核心层优先级 |
| L3 | MCP Support Internals | 有价值，但更多是局部内核深化 |
| L3 | 更复杂 lifecycle manager | 依赖前面 primitive 先稳定 |
| L3 | 多 agent / teammate 协作层 | 更适合成熟阶段再深化 |

长期主线判断也很明确：

> 未来最值钱的不是“服务更多”，而是把 `Conversation Runtime + Recovery + Runtime Events` 做成你们系统自己的稳定 primitive。

## 分项说明

下面按 9 类可吸收项逐项说明。

### 1. Conversation Runtime

- 参考点：统一对话执行核心
- 参考证据：`src/QueryEngine.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：`orchestrator.go` 已有 turn 区分、provider 调用、tool resolve/execute、max turn 循环，但整体仍偏“流程拼接”，还不是厚 runtime
- 当前优先级：`P0`
- 长期价值：`L1`

为什么值得学：

- 参考架构把多轮对话、工具调用、预算、结构化输出、失败处理、恢复入口尽量收在一个执行核心里，工程一致性很强。
- 你们现在的多服务边界是对的，但 `Gateway` 内部还缺一个更稳定的“会话执行内核”，导致很多能力仍像在外层补丁式叠加。
- 一旦 `Conversation Runtime` 成型，后续 `plan / recovery / tool events / process supervision` 都有了统一落点。

为什么不是更低：

- 这是当前最核心的缺口，直接决定后续过程结构化能否自然内生。

吸收边界：

- 只吸收“统一执行核心”的设计思想，不吸收其单体部署形态。
- 不把 `Tool Router` 的执行职责回收到 `Gateway`。

### 2. Context Assembly

- 参考点：system/user/tool/workspace 上下文统一装配
- 参考证据：`src/context.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：当前已能按 mode、plugins、retrieval roots、`user_email`、execution targets 做部分装配，但仍偏散落
- 当前优先级：`P1`
- 长期价值：`L2`

为什么值得学：

- 参考架构不是临时拼 prompt，而是把会话所需上下文视为统一装配层。
- 对你们来说，这能统一 mode、plugin、workspace、retrieval、user capability、available execution targets 等注入方式。
- 训练前如果上下文来源不统一，后续做过程样本抽取会很痛苦。

为什么不是更高：

- 它很重要，但如果没有前面的 `Conversation Runtime` 和 `Runtime Event Model`，单独做上下文装配收益会打折。

吸收边界：

- 聚焦 `Gateway` 的上下文装配，不扩大到重写整个控制面配置体系。

### 3. Plan / Recovery Layer

- 参考点：plan 生命周期、resume、fork、snapshot、一致性检查
- 参考证据：`src/utils/plans.ts`、`src/utils/conversationRecovery.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：系统级服务恢复和启动控制已经不错，但会话级 `plan / recovery` 仍未成为一等公民
- 当前优先级：`P0`
- 长期价值：`L1`

为什么值得学：

- 对比赛和训练都很实用。比赛里它提升中断恢复和长任务连续性，训练里它提升轨迹回放与过程抽样质量。
- 参考架构已经把 plan 文件、resume/fork、transcript 恢复和一致性检查做成标准流程，而不是零散辅助逻辑。

为什么不是更低：

- 它与 `Conversation Runtime` 和 `Runtime Event Model` 一起构成最值得优先补的内核三件套。

吸收边界：

- 重点吸收会话级恢复，不动 `Admin` 的服务级启停与自检边界。

### 4. Session Continuity

- 参考点：transcript 组织、恢复点、跨重启续接
- 参考证据：`src/utils/conversationRecovery.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：当前有 session logs 和 tool logs，但还缺“会话如何续接”的统一语义
- 当前优先级：`P1`
- 长期价值：`L2`

为什么值得学：

- 它解决的是“同一会话怎样持续”，而不是“计划本身怎么管理”。
- 和 `Plan / Recovery` 的区别要写清：前者偏执行目标与计划状态，后者偏 transcript、消息、恢复点与续接体验。

为什么不是更高：

- 它很依赖更前面的 runtime 核心和恢复层先收口，否则只是在日志上做文章。

吸收边界：

- 只做会话连续性设计，不演化成新的产品层交互工程。

### 5. Runtime Event Model

- 参考点：turn、tool、failure、fallback、budget、structured state 的统一事件建模
- 参考证据：`src/QueryEngine.ts`、`src/utils/commandLifecycle.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：你们已有 session logs、tool logs、SSH runtime、terminal structured result，但缺一套统一事件语义
- 当前优先级：`P0`
- 长期价值：`L1`

为什么值得学：

- 当前训练前最需要的不是更多日志，而是可复用、可比较、可抽样的过程事件。
- 统一事件模型后，`solve_rate`、`invalid_tool_call_rate`、`shell_mismatch_rate`、`error_recovery_turns` 这类指标会更自然落地。
- 它也是把 `Gateway`、评测、训练样本转换三者接起来的关键桥梁。

为什么不是更低：

- 这项对训练前封板的直接收益极高，不能等到后面再补。

吸收边界：

- 统一的是语义模型，不是要求把所有日志存储实现收进同一服务。

### 6. Tool Result Persistence / Context Compaction

- 参考点：大工具结果落盘、结果预览、内容替换引用、上下文压缩、重复结果去膨胀
- 参考证据：`src/utils/toolResultStorage.ts`、`src/utils/contextAnalysis.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：`Tool Router` 已返回结构化字段，terminal/SSH 也有分阶段结构化结果，但大输出如何进入长会话上下文仍然偏薄
- 当前优先级：`P0`
- 长期价值：`L2`

为什么值得学：

- 这是原稿最容易漏掉、但实际上非常关键的一项。
- 对安全题和本地终端来说，大日志、大反编译输出、长命令结果是常态，不做持久化与压缩，很快就会污染上下文。
- 参考架构已经把“结果存储”和“上下文瘦身”做成独立中间层，这对你们训练前的数据质量和对话稳定性都非常值钱。

为什么不是更低：

- 它直接影响长会话质量、token 成本、过程抽样质量和工具结果可引用性，短期收益非常高。

吸收边界：

- 优先在 `Gateway` 侧做结果引用和上下文治理，不改 `Tool Router` 的执行边界。

### 7. Tool Schema / Metadata Cache

- 参考点：工具 schema 缓存、动态工具信息稳定化
- 参考证据：`src/utils/toolSchemaCache.ts`
- 当前系统落点：`Gateway`
- 当前系统现状：当前终端 OpenAPI 描述已经能注入 `available_execution_targets` 等动态信息，但缺少更明确的 schema 稳定化策略
- 当前优先级：`P1`
- 长期价值：`L2`

为什么值得学：

- 参考架构很清楚地把 schema 缓存视为上下文稳定性的组成部分，而不只是性能优化。
- 对你们来说，这能帮助稳定 terminal 工具描述、用户级执行目标描述、MCP 可见性等动态工具元信息。

为什么不是更高：

- 它重要，但更像 P0 稳住之后的增强项。

吸收边界：

- 聚焦 schema 与元信息稳定化，不额外引入新的工具协议形态。

### 8. Command Queue / Scheduling

- 参考点：命令优先级队列、排队、订阅通知、执行顺序控制
- 参考证据：`src/utils/messageQueueManager.ts`、`src/utils/commandLifecycle.ts`
- 当前系统落点：优先 `Gateway`，次级参考 `Tool Router`
- 当前系统现状：`Tool Router` 的 SSH 层已有 `queue_wait_ms`、连接池、并发槽位，但会话级任务调度仍不成体系
- 当前优先级：`P1`
- 长期价值：`L3`

为什么值得学：

- 这项值得被单列，不能再被笼统塞进 lifecycle。
- 参考架构把优先级、排队状态、通知机制做成独立原语，这对长任务、恢复、插队、会话中断都很有帮助。
- 你们现有 SSH runtime 已经证明“执行层排队”是刚需，下一步更应该关注“会话层排队”。

为什么不是更高：

- 当前训练前最缺的还是 runtime 事件和结果沉淀，不是更复杂的排队语义。

吸收边界：

- 主要吸收调度思想，不要因此重写 `Tool Router` 的执行模型。

### 9. MCP Support Internals

- 参考点：校验、缓存、结果存储等内部 MCP 中间层
- 参考证据：参考源码中的 MCP validation / output storage 相关模块
- 当前系统落点：`Gateway / Admin`
- 当前系统现状：你们在 MCP 控制面、preview、runtime、discover、Open WebUI 同步方面已经走得比参考架构更贴比赛场景
- 当前优先级：`P2`
- 长期价值：`L3`

为什么值得学：

- 可借鉴其校验、缓存、输出存储的内部组织方式。
- 尤其是在统一工具元信息、减少重复校验、沉淀过程结果方面仍有参考价值。

为什么不是更高：

- 你们当前 MCP 真正的短板并不在“有没有 MCP 控制面”，而在会话 runtime 还未充分结构化。
- 现在若把注意力先放在 MCP internals，很容易偏离训练前封板主线。

吸收边界：

- 只吸收内部组织方式，不新增新的 MCP 协议类型，也不改当前控制面接口形态。

## 当前不建议优先吸收的部分

以下内容即使长期可能有价值，当前也不建议优先推进：

### 1. 更深的一体化 runtime 大重构

原因：

- 容易把现在清晰的服务边界重新糊掉
- 对比赛稳定性的即时收益不一定最高
- 风险明显高于“在 Gateway 内低风险内收”

### 2. 更复杂的 lifecycle / activity manager

原因：

- 这是建立在前面 `Conversation Runtime + Runtime Event Model + Recovery` 已经稳定的前提上
- 现在做容易过度设计

### 3. 多 agent / teammate 风格机制

原因：

- 这类能力长期可以做，但当前不是训练前和比赛稳定性的主阻塞项
- 容易把注意力从主线拉走

### 4. 任何把多服务重新并回单体的改法

原因：

- 会直接破坏你们现有最有价值的边界：`Control Plane / Execution Plane`
- 诊断性、隔离性、可恢复性都会受损

## 最终建议

这份清单的最终建议可以压成三句话：

1. 保持现有多服务边界不动，不做“参考架构整套迁入”。
2. 近期只补 `Gateway` 内部四件事：`Conversation Runtime`、`Runtime Event Model`、`Tool Result Persistence / Context Compaction`、`Plan / Recovery Layer`。
3. 等这四项收稳后，再补 `Context Assembly`、`Session Continuity`、`Tool Schema / Metadata Cache`、`Command Queue / Scheduling`，而不是把主战场先转去 `MCP internals` 或大重构。

如果只用一句话总结本文结论：

> 保留你们现在正确的多服务外形，优先吸收参考架构在 `Gateway` 内部 runtime 厚度上的成熟做法，而不是照搬它的系统形态。
