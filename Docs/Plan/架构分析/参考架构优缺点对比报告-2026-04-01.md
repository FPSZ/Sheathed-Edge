# 参考架构优缺点对比报告

日期：2026-04-01

## 结论摘要

这次参考架构的核心价值，不在于它是一个“更先进的完整替代品”，而在于它把 `Conversation Runtime` 做得很厚，很多能力已经被抽象成稳定的一等公民，例如：

- 会话上下文装配
- 多轮执行核心
- plan 生命周期
- 恢复与快照
- 工具调用状态
- 结构化输出与预算控制

从恢复源码看，参考项目更像一个“单 runtime、厚内部抽象、强会话内编排”的 agent 系统。它的重点是把 agent 在一次会话里如何思考、如何调用工具、如何恢复、如何持续执行，尽量收束到统一执行内核里。

你们当前系统则明显不是这条路线。现有架构更像一个“多服务拆分、控制面和执行面明确分离、适合比赛运维和故障定位”的本地 AI 系统：

- `Open WebUI` 负责前端交互
- `Gateway` 负责模型协议、模式装配、部分工具编排
- `Tool Router` 负责 terminal / SSH / MCP 等执行面
- `Admin` 负责控制面、自检、配置和运行态观测
- `llama-server` 与 `host-agent` 作为独立下游服务存在

所以这两套架构不是简单的“谁比谁先进”，而是优化目标不同：

- 参考架构强在 agent runtime 内核
- 你们当前架构强在比赛场景下的系统边界、恢复、自检、隔离和运维透明度

本报告的核心结论是：

1. 不建议把你们当前多服务边界推翻，改造成参考项目那种单体 agent 内核。
2. 强烈建议吸收参考架构在 `QueryEngine / plan / recovery / transcript snapshot / context assembly / tool lifecycle` 这些内部抽象上的做法。
3. 下一阶段最值得做的不是“重构成另一个系统”，而是保持当前 `Execution Plane` 和 `Control Plane` 不动，在 `Gateway` 内部补一层更完整的 `Conversation Runtime`。

## 参考架构概览

### 1. 架构本质

参考项目从恢复源码看，核心不是“多个服务如何通信”，而是“一个 agent runtime 如何把整个会话跑稳”。最关键的入口和骨架包括：

- `src/main.tsx`
- `src/context.ts`
- `src/QueryEngine.ts`
- `src/utils/plans.ts`
- `src/utils/conversationRecovery.ts`
- `src/utils/commandLifecycle.ts`
- `src/utils/toolSchemaCache.ts`
- `src/utils/toolResultStorage.ts`
- `src/utils/mcpValidation.ts`

其中最值得注意的是，它并不是把计划、上下文、恢复这些能力散落在很多外围逻辑里，而是尽量把它们做成 runtime 的标准组件。

### 2. 参考架构的主要强项

#### 2.1 厚会话运行时

`src/QueryEngine.ts` 明确承担了会话执行核心的职责。它不仅仅是一个“发请求拿回答”的包装器，而是把以下逻辑统一收口：

- 当前工作目录与会话状态
- 多轮消息追加
- 工具权限决策与拒绝记录
- 技能与插件装载
- 预算限制
- 最大轮次限制
- 结构化输出重试
- transcript 记录
- 部分流式事件处理
- 中断控制

这意味着参考架构对“多轮 agent 行为”有一个明确的内核对象，而不是每层都带一点状态、每层都处理一点异常。

#### 2.2 上下文注入层成熟

`src/context.ts` 里能看到比较清晰的 `system context` 和 `user context` 分层：

- git 状态快照
- 当前日期
- Claude MD / memory 文件
- cache breaker
- bare mode / env flag 控制

这种设计的优点在于，会话上下文是“组装出来的”，不是临时散落到 prompt 拼接逻辑里。对于后续做训练、评测、过程监督，这种统一装配方式很重要，因为它天然更容易审计、复现和固化。

#### 2.3 plan 与恢复机制是一等公民

`src/utils/plans.ts` 暴露出来的不是一个简陋的“写个 markdown 文件”能力，而是完整的 plan 文件生命周期：

- 每个 session 有 plan slug
- 支持 resume 时恢复
- 支持 fork 时复制到新 slug
- 在远程环境下支持从 transcript 快照恢复 plan
- 会把 plan 作为 conversation lifecycle 的一部分考虑

这类设计对长对话恢复、多人协作、训练时回放轨迹，都非常有价值。

#### 2.4 工具与恢复相关基础设施丰富

从恢复源码模块名看，参考项目已经围绕工具与运行生命周期积累了很多实用层：

- `toolSchemaCache`
- `toolResultStorage`
- `mcpOutputStorage`
- `messageQueueManager`
- `activityManager`
- `commandLifecycle`
- `conversationRecovery`

这说明它不是仅仅能“调工具”，而是已经开始把工具调用变成一个可恢复、可观察、可约束的内部系统。

### 3. 参考架构的主要弱项

#### 3.1 更偏单体 runtime

参考架构的强项几乎都在内部运行时，但这也意味着它更像一个厚单体。它对“服务间硬隔离、独立运行态、控制面和执行面分离”的强调，不如你们当前系统强。

对于比赛环境，这会带来几个潜在问题：

- 某个内部机制出问题时，可能更难通过外部控制面迅速定位
- 运维层、执行层、会话层可能纠缠更深
- 如果直接照搬，会冲击你们当前已经很有价值的服务边界

#### 3.2 不天然适配多宿主机和比赛控制面

你们现在已经把这些需求拉到了前台：

- 本地 terminal
- SSH terminal
- MCP runtime
- 用户级执行目标授权
- Admin 自检与服务控制

参考架构虽然在内部 agent 抽象上更成熟，但它的核心设计目标并不是“多宿主机比赛控制面”。所以它更适合作为内部 runtime 设计的灵感来源，而不是整体部署形态的模板。

#### 3.3 若原样迁移，容易破坏现有清晰边界

如果直接把参考架构思路整包迁入，最容易出现的误区是：

- 把 Gateway 继续做厚，连 Tool Router 和 Host Agent 的职责也往里收
- 把控制面、执行面、会话面重新揉在一起
- 为了模仿“优雅的 agent runtime”，牺牲比赛时最需要的故障隔离与透明度

这是本报告最明确反对的方向。

## 我们当前架构概览

### 1. 架构本质

根据 [`Agent/http-contract.md`](/D:/AI/Local/Agent/http-contract.md)，你们当前主链非常明确：

1. 用户在 `Open WebUI` 发起对话
2. `Open WebUI` 把模型流量发给 `Gateway`
3. `Gateway` 负责模式装配与模型协议兼容
4. `Gateway` 调用 `llama-server`
5. 需要工具时，`Gateway` 或 `Open WebUI` 调 `Tool Router`
6. `Tool Router` 执行 terminal / SSH / MCP 等工具
7. `Admin` 提供运行态控制、自检和配置能力

这套系统的重点，是把系统拆成几个职责明确的平面：

- `Conversation Runtime`
- `Execution Plane`
- `Control Plane`
- `Model Serving Plane`

### 2. 当前架构的主要强项

#### 2.1 系统边界清楚

当前系统把几个高风险、高耦合点拆开了：

- `Gateway` 不直接吞掉所有执行逻辑
- `Tool Router` 作为独立执行面，专门处理 terminal / SSH / MCP
- `Admin` 作为独立控制面，负责用户工作区、SSH、MCP、日志、自检

这种边界对比赛非常重要，因为它让“功能能不能用”和“哪一层出了问题”更容易区分。

#### 2.2 控制面能力已经明显优于典型 agent runtime

从 `Agent/gateway-go/internal/gateway/transport/openai/admin.go` 可以看出，你们已经把很多比赛必要能力做成了真正的控制面接口：

- `/internal/admin/users/workspace`
- `/internal/admin/terminal-paths`
- `/internal/admin/ssh/hosts`
- `/internal/admin/ssh/hosts/test`
- `/internal/admin/ssh/hosts/confirm-host-key`
- 以及 model / modes / session logs / tool logs 等接口

这不是“附带一个设置页”，而是已经形成了较明确的 `Control Plane`。

#### 2.3 执行面隔离做得对比赛友好

`Agent/tool-router-rs/src/api.rs` 与 `src/ssh.rs` 里可以看到，terminal 和 SSH 已经被当成独立执行面来设计，而不是当成某个 prompt hack 的附庸：

- OpenAPI tool server 对外暴露统一 terminal 接口
- 支持 `local` 与 `ssh` 两类执行目标
- 响应里有结构化字段，如 `failure_phase`、`connection_reused`、`queue_wait_ms`
- SSH 层有运行时池、并发控制、空闲回收、错误相位

这说明你们并不是“会调 SSH”而已，而是在朝比赛级执行基础设施走。

#### 2.4 多执行目标和用户授权方向合理

从 OpenAPI 描述与代码痕迹可以看出，你们已经在往“同一会话内按调用自行切换本机与 SSH”推进，同时还考虑：

- `user_email`
- `available_execution_targets`
- 每用户授权可见目标

这条路线非常适合你们的真实比赛需求，也明显比很多通用 agent runtime 更贴地。

### 3. 当前架构的主要短板

#### 3.1 Gateway 内部会话执行核心还不够厚

虽然 `Agent/gateway-go/internal/gateway/orchestrator/orchestrator.go` 已经体现出一定的 turn orchestration 能力，例如：

- mode 装配
- retrieval 选择
- conversation vs tool turn 区分
- native tool prompt 与 legacy envelope 流程

但和参考项目的 `QueryEngine` 比，当前 Gateway 内部还是偏薄：

- 没有统一的会话生命周期对象
- plan / recovery / transcript snapshot 不是标准内建能力
- tool lifecycle、budget、structured output 等没有进入同一执行核心

这会导致后续很多能力继续以“补丁形式”堆在外围。

#### 3.2 过程结构化沉淀还不够

你们已经有：

- `Datasets`
- `Eval`
- `Skills`
- `Admin logs`
- `Tool logs`

但 agent 在一次对话里到底怎么选工具、为什么切目标、失败后怎么恢复，这些“过程状态”还没有像参考架构那样被收成标准 runtime 事件。

对后续训练来说，这会带来两个问题：

1. 很难稳定抽取高质量过程监督样本
2. 很难把 plan、tool turn、fallback、失败原因一体化对齐

#### 3.3 部分能力仍显得像服务拼接而不是统一 runtime primitive

你们现在的整体系统方向是对的，但内部仍能感受到一些阶段性痕迹：

- 某些逻辑在 Gateway
- 某些逻辑在 Tool Router
- 某些逻辑在 Admin
- 某些逻辑还停留在 prompt / schema / 外围约束层

这并不是错，而是说明当前系统已经具备良好的系统边界，但还没完成“内部 agent runtime 的第二次收口”。

## 逐维度优缺点对比

### 1. 系统拓扑

参考架构优点：

- 单 runtime 内部一致性强
- 会话相关能力更容易集中管理
- 计划、恢复、工具生命周期天然更统一

参考架构缺点：

- 运维边界不如多服务系统清晰
- 不天然适合比赛环境的控制面和故障隔离

当前架构优点：

- 多服务边界清楚
- `Control Plane` 与 `Execution Plane` 分离合理
- 更适合比赛时快速排障和恢复

当前架构缺点：

- 会话级能力分散在多个服务和接口之间
- 内部统一 runtime 感还不够强

### 2. 会话与上下文层

参考架构优点：

- `context.ts` 体现出清晰的 system/user context 注入模型
- 上下文缓存、git 状态、memory 文件、日期等都能标准化进入会话

参考架构缺点：

- 更偏单 runtime 语境，外部控制面与上下文策略的联动不明显

当前架构优点：

- 模式、插件、工具边界更清楚
- 外部服务更容易根据场景做隔离部署

当前架构缺点：

- 缺少统一的上下文装配层概念
- session / workspace / tool availability / user capability 注入还可进一步标准化

### 3. 任务、计划与恢复层

参考架构优点：

- plan 是一等公民
- resume / fork / snapshot 恢复机制成熟
- 长会话和远程恢复思路完整

参考架构缺点：

- 这套能力深嵌在单 runtime 内，迁移成本高

当前架构优点：

- 外部服务恢复和进程级恢复思路更强
- 比赛型冷启动、自检、服务控制有更好基础

当前架构缺点：

- 会话级恢复、plan lifecycle、tool turn replay 还不够系统化

### 4. 工具与执行层

参考架构优点：

- 工具 schema、工具结果、工具生命周期抽象更完整
- 多轮工具协作更容易收口到同一执行内核

参考架构缺点：

- 对独立运行态 SSH/MCP/terminal 的强调不如你们强

当前架构优点：

- `Tool Router` 是非常对路的设计
- terminal / SSH / MCP 独立成为执行面，适合安全边界和审计
- 运行态观测、错误分类、执行目标切换都更贴合真实比赛

当前架构缺点：

- 工具调用过程在系统内部还没被建模成更高层次的 conversation runtime event

### 5. 控制面与可观测性

参考架构优点：

- 对 agent 内部状态的建模更细

参考架构缺点：

- 没有像你们这样把管理能力拉成独立控制面
- 对服务级自检、用户级 SSH/MCP 授权、多执行目标控制的支撑思路不突出

当前架构优点：

- `Admin` 路线非常适合比赛场景
- 自检、日志、SSH、MCP、用户工作区这些能力都已经有控制面雏形
- 对“哪个用户能看到哪些执行目标”这种问题，当前架构比参考项目更有落地基础

当前架构缺点：

- 控制面强，运行时内核相对薄
- 有时会出现“外部看得很清楚，内部状态表达还不够统一”的反差

### 6. 扩展与训练衔接

参考架构优点：

- plan、恢复、tool result、context assembly 都非常适合后续做过程监督
- 如果想做结构化轨迹与评测，参考项目的内部形状很值得学习

参考架构缺点：

- 不一定适合直接承载你们已经成型的多服务比赛系统

当前架构优点：

- `Datasets / Eval / Skills / Admin logs / Tool logs` 外层已经有训练闭环基础
- 与本地比赛环境和离线要求更契合

当前架构缺点：

- 训练前最该补的是内部过程结构化，而不是继续加外围功能

## 值得学习的设计

以下内容建议吸收，但要以“内收 Gateway runtime、外部边界不变”为原则。

### 1. 在 Gateway 内形成 `QueryEngine` 式执行核心

目标不是复制参考项目文件结构，而是把当前零散的会话逻辑收成一个统一对象，至少统一这些内容：

- 当前会话消息
- turn 状态
- tool turn 与 normal turn 区分
- 预算与回合限制
- 结构化输出约束
- 失败重试与恢复钩子
- 过程事件输出

### 2. 把 plan / recovery / transcript snapshot 做成标准机制

这一点对你们后续训练尤其重要。建议未来把以下内容变成标准资产：

- 当前会话 plan
- 关键 turn 的状态快照
- tool 调用摘要
- 失败恢复节点
- 可供训练抽取的结构化轨迹

### 3. 建立统一上下文装配层

建议把这些内容从“哪里用到哪里拼”升级为统一注入：

- workspace 信息
- 当前用户能力
- 可用执行目标
- 当前模式与插件
- retrieval 边界
- 当前日期、git、环境摘要

### 4. 为工具调用建立标准生命周期事件

后续训练、评测、回归最需要的，不只是日志，而是结构化事件：

- 为什么选这个工具
- 目标是 local 还是 ssh
- 期望证据是什么
- 实际结果是否命中
- 失败落在哪个 phase
- fallback 是什么

### 5. 借鉴参考架构的恢复思路，而不是复制其部署形态

这点很重要。值得借鉴的是：

- 恢复机制
- transcript/plan 关联方式
- lifecycle 管理

不值得借鉴的是把它们重新塞回一个单体里。

## 不建议照搬的设计

### 1. 不要把现有多服务边界收回单体

当前 `Admin + Gateway + Tool Router + Host Agent + llama-server` 的边界非常有价值。不要为了追求内部优雅，把它们重新揉成一个“大 agent 进程”。

### 2. 不要削弱 terminal / SSH / MCP 的独立执行面

你们比赛时真正会依赖的是：

- 本机执行
- SSH 执行
- MCP 调用
- 用户级授权
- 失败隔离

这些能力作为独立 `Execution Plane` 是正确方向。

### 3. 不要为了模仿参考架构而牺牲运维透明度

当前系统最大的现实优势之一，就是出了问题能区分：

- 是服务没起
- 是 Gateway 失败
- 是 Tool Router 失败
- 是 SSH host 问题
- 是 MCP runtime 问题

这类透明度在比赛里远比“内部抽象看起来更统一”重要。

### 4. 不要把训练前重点放成“大重构”

你们当前最缺的不是“换架构”，而是：

- 内部 runtime 收口
- 过程事件结构化
- plan / recovery 标准化

如果现在去做大范围架构重写，收益未必高，风险反而很大。

## 对我们下一阶段的架构建议

### 近期

保持现有多服务边界不动，重点补 `Gateway` 内部运行时能力：

- 增加统一会话执行核心
- 增加 plan / recovery / runtime event 结构
- 把工具调用过程做成标准事件流

### 中期

在不动 `Tool Router` 和 `Admin` 边界的前提下，让 `Gateway` 真正成为稳定的 `Conversation Runtime`：

- 统一 normal turn / tool turn / recovery turn
- 统一 prompt context assembly
- 统一 tool lifecycle 记录

### 训练前

优先补能直接提升训练数据质量的能力：

- 过程结构化
- 失败恢复标注
- 会话 plan 与工具轨迹关联
- 评测与日志的统一事件模型

### 训练后

再考虑是否进一步把更多 agent runtime 抽象内生化，但前提仍然是：

- 不破坏多服务边界
- 不削弱 `Admin`
- 不削弱 `Tool Router`
- 不影响比赛可恢复性与可诊断性

## 最终判断

参考架构真正值得学习的，不是它“看起来像一个成熟 agent 产品”，而是它把 agent 的很多内部过程做成了标准 runtime 机制。你们当前系统真正值得坚持的，也不是“我们已经有很多服务”，而是你们已经选对了比赛系统的边界。

所以最优路线不是二选一，而是组合：

- 外部保持你们现有的多服务、控制面、执行面拆分
